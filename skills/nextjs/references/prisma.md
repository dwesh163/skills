Not every app in this stack owns a database at all — a thin BFF over an
external API (services-and-errors.md's Shape B) or an app backed by
something else entirely (e.g. Kubernetes/Helm releases standing in for a
data store) has no Prisma module. Check whether the app actually owns data
before assuming it needs this.

When it does: Prisma 7.x, schema **not** at the repo root — it lives under
`src/prisma/`. The generated client is custom-output and gitignored.

## Layout

```
src/prisma/
  schema.prisma
  migrations/
  seed.ts
  zod-generator.config.json   — optional, see validation.md
prisma.config.ts               — repo root, Prisma 7's config file (replaces the
                                  package.json "prisma" key from Prisma <7)
generated/prisma/              — repo root, gitignored, generated client output
src/lib/prisma.ts              — the client singleton
```

## `prisma.config.ts`

```ts
// This file was generated by Prisma, and assumes you have installed the following:
// npm install --save-dev prisma dotenv
import "dotenv/config";
import { defineConfig } from "prisma/config";

export default defineConfig({
  schema: "src/prisma/schema.prisma",
  migrations: { path: "src/prisma/migrations", seed: "tsx src/prisma/seed.ts" },
  datasource: { url: process.env.DATABASE_URL },
});
```

## `schema.prisma`

```prisma
generator client {
  provider = "prisma-client"
  output   = "../../generated/prisma"   // relative to src/prisma/, resolves to <root>/generated/prisma
}

datasource db {
  provider = "postgresql"
}

// user / session / account / verification — better-auth's own tables, see below
```

`provider = "prisma-client"` (not `prisma-client-js`) is Prisma 7's ESM
client generator. Names are snake_case in the database and camelCase in
TypeScript — see the next section.

Some older repos in this stack colocate the generated client at
`src/prisma/generated/` instead of a root-level `generated/`; either is fine
as long as it's gitignored and the import paths are relative (see
file-organization.md) — match whichever an existing repo already does, don't
migrate it as a drive-by change.

## Names: snake_case in the database, mapped everywhere

No identifier in Postgres has a capital letter: no `"Stagiaire"` table, no
`"workspaceId"` column. The Prisma side keeps PascalCase models and camelCase
fields (so the TypeScript code never changes), and the schema maps **every**
name that would otherwise carry a capital:

- **Every model** gets `@@map("snake_case")`, singular like the model
  (`StagiaireTag` → `stagiaire_tag`) — including better-auth's.
- **Every field with a capital in it** gets `@map("snake_case")`:
  `createdAt`/`updatedAt` → `created_at`/`updated_at`, every `xxxId` foreign key
  → `xxx_id`, and the rest the same way (`firstName` → `first_name`,
  `wpformsId` → `wpforms_id`). One-word fields (`name`, `status`) need nothing.
- **Every enum** gets `@@map("snake_case")` (`StageStatus` → `stage_status`). The
  values stay `UPPER_CASE`, they are data, not identifiers.

```prisma
model StagiaireTag {
  stagiaireId String   @map("stagiaire_id")
  tagSlug     String   @map("tag_slug")
  createdAt   DateTime @default(now()) @map("created_at")

  @@id([stagiaireId, tagSlug])
  @@index([tagSlug])
  @@map("stagiaire_tag")
}

enum StageStatus {
  PLANNED
  OPEN

  @@map("stage_status")
}
```

Relation fields (`stagiaire Stagiaire @relation(...)`) have no column, so no
`@map`. Indexes, keys and foreign keys need no `map:` argument either: Prisma
builds their names from the mapped names (`stagiaire_tag_tag_slug_idx`).

**Raw SQL speaks the database's names**, not the schema's, and needs no
quotes any more: `` $queryRaw`SELECT id FROM stage WHERE workspace_id = ${id}` ``,
not `"Stage"` and `"workspaceId"`. `grep` for `$queryRaw`/`$executeRaw` after
renaming anything.

### Renaming an existing database

Adding `@map`s to a schema whose tables already exist makes
`prisma migrate dev` generate a `DROP TABLE` + `CREATE TABLE` for each one —
and the data goes with them. Don't accept that migration; write it by hand with
renames, in this order:

1. `ALTER TYPE … RENAME TO` for the enums, `ALTER TABLE … RENAME TO` for the
   tables, then `ALTER TABLE … RENAME COLUMN … TO` for the columns.
2. Rename what carries the old names: primary keys and foreign keys with
   `ALTER TABLE … RENAME CONSTRAINT`, other indexes with `ALTER INDEX … RENAME TO`.
   Prisma's default names are `<table>_pkey`, `<table>_<columns>_idx|key|fkey`,
   built from the *new* names, and it reports drift for any other name.
3. Rename the leftovers Prisma does not look at: `CHECK`s added by hand in
   earlier migrations, and on Postgres 18 the `<table>_<column>_not_null`
   constraints, which keep the names they were created with. A `DO` loop over
   `pg_constraint` (`contype = 'n'`) does the latter and is a no-op on older
   versions.

Then check it on a copy of the data before touching the real database, and
prove the schema and the database agree (empty diff, exit code 0):

```
pg_dump dev | psql scratch      # a copy of the data, in a scratch database
psql -1 -f migration.sql scratch
DATABASE_URL=…/scratch prisma migrate diff --from-config-datasource \
  --to-schema src/prisma/schema.prisma --exit-code --script
```

Replay all the migrations on an empty database too (`prisma migrate deploy`,
then the same diff): that is what a fresh checkout or a first deploy runs.

## Auth tables — generated, not hand-written

better-auth (see auth.md) needs `user`, `session`, `account`, and
`verification` tables — a real DB-backed session, not just a `User` row the
way a JWT-cookie-based auth library needed. Generate this part of the
schema instead of hand-writing it:

```
bunx @better-auth/cli generate
```

This reads the `betterAuth({...})` config (including any
`user.additionalFields` entries) and writes/updates the matching Prisma
models. Re-run it after adding an `additionalFields` entry or a new plugin
that needs its own table — don't hand-edit the generated models to add a
field, add it to the `betterAuth()` config and regenerate, the same way
`components/ui/` is edited by regenerating, not by hand (see tooling.md).
Every plugin mentioned in auth.md/permissions.md/stripe.md adds to this
generated surface the same way: the `admin` plugin adds a `role`/`banned`
set of columns to `user`; `organization` adds `organization`/`member`/
`invitation` tables; `twoFactor` adds its own table (TOTP secret, backup
codes) plus a `twoFactorEnabled` column on `user`; `@better-auth/stripe`
adds a `subscription` table and a `stripeCustomerId` column on `user`.
Regenerate after adding any of them, same command, same workflow. The rest
of the schema (every domain model) stays entirely hand-written as normal; only the
auth-and-plugin tables are CLI-managed.

The CLI writes the camelCase columns without any `@map` (the table only gets its
`@@map`), so the naming rule above is the one hand edit these models need: map
every multi-word field (`emailVerified` → `email_verified`, `userId` → `user_id`,
`createdAt` → `created_at`…). better-auth reads and writes through the Prisma
field names, so nothing else changes. Look at the `git diff` of the schema after
each regeneration and put back any `@map` it dropped.

## `src/lib/prisma.ts` — the singleton

Uses the `pg` driver adapter (not Prisma's built-in connection handling) and
the standard Next.js dev-hot-reload-safe global singleton. `PrismaPg` takes the
connection string directly — no hand-built `Pool` and no
`as unknown as ConstructorParameters<...>` cast:

```ts
import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient } from "../../generated/prisma/client";

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined };

const adapter = new PrismaPg(process.env.DATABASE_URL ?? "");

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({ adapter, log: process.env.NODE_ENV === "development" ? ["error", "warn"] : ["error"] });

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;
```

Without the `globalThis` cache, Next.js's dev-mode module reloading creates a
new `PrismaClient` (and a new connection pool) on every hot reload, quickly
exhausting Postgres's connection limit.

## Bootstrapping gotchas

- **Pin the CLI to the client's version.** `bun add -d prisma` can resolve a
  newer major (an 8.x RC) than `@prisma/client`/`@prisma/adapter-pg` (7.x). Run
  `bun add -d prisma@<same version as @prisma/client>`.
- **Chicken-and-egg with the better-auth CLI.** `@better-auth/cli generate`
  imports `src/lib/auth/server.ts`, which imports `src/lib/prisma.ts`, which
  imports the generated client. On a fresh project, write a schema with just
  the `generator` + `datasource`, run `bunx prisma generate` (works with zero
  models), *then* `bunx @better-auth/cli@latest generate --config
  src/lib/auth/server.ts --output src/prisma/schema.prisma -y`, then
  `bunx prisma migrate dev --name init`. Export `.env` first (`set -a; . ./.env`).
- **No `postinstall: prisma generate`** — the Dockerfile `deps` stage only copies
  `package.json`/lockfile, so there is no schema yet and install would fail.
  Generate in `dev`/`build` scripts and in the builder stage instead.

## Local dev database

Postgres runs in Docker Compose next to the dev server, started by `make up`
(a `Makefile` + `docker-compose.dev.yml` — see local-dev.md), not an inline
`docker run` stuffed into `package.json`. Compose applies the migrations
(`prisma migrate deploy`) once Postgres is healthy, before the dev server
starts. `package.json`'s own scripts stay plain:

```json
"dev": "bunx prisma generate && next dev",
"build": "prisma generate && next build"
```

`build` always regenerates the client first — the generated output is
gitignored, so a fresh checkout/CI runner has nothing to import from without
this.

## Dockerfile

When the app has a Prisma module, the Docker builder stage must run
`prisma generate` before `next build` — it's the only way the builder gets a
client, since `generated/` isn't checked in:

```dockerfile
RUN bunx prisma generate
RUN node node_modules/.bin/next build   # with the inline env placeholders from tooling.md
# (BETTER_AUTH_SECRET, BETTER_AUTH_URL and a dummy DATABASE_URL — PrismaPg is built at import time)
```
