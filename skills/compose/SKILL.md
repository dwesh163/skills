# Local dev environment

The whole dev stack runs in Docker Compose: the database, any backing service, **and** the application's dev server. `make up` is the only command a developer types. Onboarding is "install Docker, get access to the secrets, `make up`", with no local runtime, package manager or database to line up.

Why: identical runtime and database versions on every machine, native dependencies built for the container instead of the host, and no `docker run` one-liner hidden in a package script.

## Three files, one job each

| File | Job |
|---|---|
| `Makefile` | Names every step, documents itself with `make help`, generates `.env` |
| `docker-compose.dev.yml` | The services of the stack, wired together |
| `.env` | Generated by `make env`, gitignored, never edited by hand; read by compose and by host tools |

## Makefile

Targets:

| Target | Does |
|---|---|
| `help` | Default goal. Lists targets from their `##` doc comments |
| `env` | Generates `.env` from the secrets file; fails if a key is missing |
| `up` | Depends on `env`, then builds and starts the stack in the foreground |
| `down` | Stops the stack |
| `logs` | Follows the app service's logs |
| `clean` | Stops containers, removes volumes and the app's build cache |

Variables, all overridable from the command line (`make VAR=value target`):

- `ENV` selects the section of the secrets file (default `dev`), so staging values need no duplicated target.
- `SECRETS_FILE`, `ENV_FILE`, `COMPOSE_FILE`, `DOCKER_COMPOSE` locate the inputs and tools.
- Ports of the local stack (`APP_PORT`, database port) are exported so compose reads them. Use a non-default database port so the stack never collides with a database running natively on the host.
- `DEBUG=1` enables shell tracing for any target.

Recipe rules:

- `SHELL` is bash, recipes run with `-e` so any failing command stops the target.
- Every target is declared `.PHONY`.
- A comment block at the top lists every target and every overridable variable.

## `make env`

Behavior the recipe must have:

- **Mapping table.** A `SECRETS` list of `ENV_VAR=path.in.secrets` pairs, one per secret the app reads, and a `LOCAL_VARS` list of values defined in the Makefile itself (local URLs, ports).
- **Fails loudly** when the secrets file is absent (telling the developer to sync it) or a key is missing (naming the key and the variable). Never a half-written `.env`.
- **Atomic write.** Write to a temporary file, remove it on failure with a `trap`, then move it into place, so an interrupted run never leaves a truncated `.env`.
- **Derived values** (a database URL built from the same credentials compose creates the database with) are computed, never stored twice, so the two cannot drift.
- **Per-developer secrets are not shared.** A session signing key, for instance, is kept from the existing `.env` when present, and generated with a cryptographic random source otherwise. Guard the read of the existing file so it does not abort the very first run on a fresh clone.
- **YAML parsing** works with both `yq` flavours (the Go and the Python implementations share a binary name but not a syntax): detect the flavour from `yq --version`, allow forcing it with a variable.
- `env` is its own target, so `.env` can be regenerated alone after a secret rotates.

## Shared secrets file

- One file in the team's secret store (a Keybase team folder, or the team's equivalent), outside every repository.
- A top-level key per environment (`dev`, `staging`, `prod`), the same nested shape under each.
- Grouped by concern (auth, database, external APIs), keys named after what they are, not after the variable that reads them.

Without a shared secret store: `env` copies `.env.example` to `.env` only when `.env` is missing, and fills generated secrets. Everything else stays identical.

## `docker-compose.dev.yml`

- **Database**: pinned major version, port published on the non-default host port, credentials from `.env` with defaults, a named volume mounted at the path the image version actually uses, and a healthcheck.
- **App**: the runtime image matching the Dockerfile and CI majors, running as a non-root user whose uid matches the usual host uid, the repository bind-mounted, `.env` loaded with `env_file`.
- **Inside the compose network, services are reached by service name.** `.env` points at `localhost` and the published port (for host tools); override that connection variable in the app service's `environment`.
- **Dependency directories and build caches live in named volumes**, mounted over the bind mount, so artifacts built for the container never land on the host. An init service running as root hands those volumes to the app user before the app starts.
- **Startup order through `depends_on` conditions**: `service_healthy` for the database, `service_completed_successfully` for the init service. No `sleep`, no separate migrate target.
- **The app's command** installs dependencies from the lockfile in frozen mode, applies pending migrations, then `exec`s the dev server.
- **`restart: on-failure`** with a small limit, so a transient network failure during dependency installation does not leave the app down.

## Easy to get wrong

- Passwords that end up in a connection URL must be URL-safe.
- The app's public URL in `.env` must match `APP_PORT`, or auth callbacks are rejected.
- `.gitignore` needs `.env*` and an exception for `.env.example`.
- `.dockerignore` excludes the Makefile, compose files, `.env*` and secrets files (see the `docker` skill).
- Package scripts stay plain: compose runs them, the Makefile starts compose.
